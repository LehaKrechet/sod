# SOD Multicast

SOD Multicast — программа для измерения задержек обмена данными между несколькими Linux-компьютерами по UDP multicast в локальной сети Ethernet.

Программа обнаруживает соседние узлы, при необходимости ожидает появления заданного количества устройств, затем выполняет циклический обмен и выводит гистограмму времени цикла. При изменении состава участников в конце ограниченного запуска печатается журнал подключений и отключений.

## Возможности

- Обнаружение устройств в локальной сети через multicast discovery.
- Обмен UDP multicast с разбиением полезной нагрузки на фрагменты.
- Размер полезной нагрузки настраивается в `config.ini`.
- Режим ожидания заданного количества устройств перед началом обмена.
- Отключение или повторное подключение узла после старта не останавливает измерения.
- Гистограмма и среднее время цикла выводятся в терминал.
- В конце ограниченного запуска выводится журнал событий подключения/отключения.
- CSV-файлы и подробное CSV-логирование не создаются.

## Требования

- Linux с поддержкой UDP multicast.
- Компилятор C++ с поддержкой C++17.
- CMake.
- Права доступа, необходимые для выбранных настроек realtime и сети.

Установка инструментов сборки в Ubuntu/Debian:

```bash
sudo apt update
sudo apt install -y build-essential cmake
```

## Сборка

Выполните из каталога проекта:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

Исполняемый файл будет создан по пути `build/sod_multicast`.

## Настройка

Перед запуском откройте `config.ini`. Для каждого компьютера задайте уникальный `node_id`. Параметры multicast и параметры протокола на всех компьютерах должны совпадать. `interface_ip` указывает IPv4-адрес сетевого интерфейса, через который выполняется обмен; рекомендуется указать адрес Ethernet-интерфейса явно, а не оставлять `0.0.0.0`, если на компьютере несколько сетевых интерфейсов.

Пример основных параметров:

```ini
node_id=1
expected_nodes=2
wait_for_nodes=true
multicast_group=239.10.10.10
data_port=5000
discovery_port=5001
interface_ip=192.168.67.3
payload_size_bytes=2048
chunk_payload_bytes=1200
cycle_period_us=1000
max_cycles=10000
receive_timeout_us=120
heartbeat_interval_ms=250
peer_timeout_ms=1500
```

Назначение основных параметров:

| Параметр | Назначение |
|---|---|
| `node_id` | Уникальный идентификатор этого компьютера. На каждом узле должен быть свой номер. |
| `expected_nodes` | Общее ожидаемое количество устройств, включая текущий компьютер. Например, `3` означает всего три узла. |
| `wait_for_nodes` | `true` — ждать обнаружения нужного числа устройств; `false` — начинать сразу. |
| `multicast_group` | Multicast IPv4-адрес группы. Должен совпадать на всех узлах. |
| `data_port` | UDP-порт обмена данными. Должен совпадать на всех узлах. |
| `discovery_port` | UDP-порт обнаружения устройств. Должен совпадать на всех узлах. |
| `interface_ip` | IPv4-адрес локального сетевого интерфейса для multicast. Укажите адрес соответствующего интерфейса каждого компьютера. |
| `payload_size_bytes` | Размер сообщения приложения в байтах. Для теста 2 КБ используйте `2048`. |
| `chunk_payload_bytes` | Максимальный размер полезной части одного UDP-фрагмента. |
| `cycle_period_us` | Целевой период между началами циклов в микросекундах; `0` — без дополнительного ожидания до следующего периода. |
| `max_cycles` | Число циклов. `0` — работать без ограничения; положительное значение — завершиться после указанного числа циклов. |
| `receive_timeout_us` | Время ожидания входящих фрагментов в рамках цикла, мкс. |
| `heartbeat_interval_ms` | Период отправки discovery-маяков. |
| `peer_timeout_ms` | Время без маяков, после которого узел считается отключившимся. |
| `cpu_affinity` | Номер CPU для привязки основного процесса; `-1` — не задавать привязку. |
| `realtime_priority` | Приоритет `SCHED_FIFO`; `0` — не включать этот режим. |
| `lock_memory` | `true` — запросить блокировку памяти процесса через `mlockall`. |

Убедитесь, что `expected_nodes` не меньше 1. Для режима ожидания число удалённых устройств равно `expected_nodes - 1`.

## Запуск

```bash
sudo ./build/sod_multicast config.ini
```

Можно передать путь к другому конфигурационному файлу вместо `config.ini`.

### Пример режима ожидания

На первом компьютере:

```ini
node_id=1
expected_nodes=2
wait_for_nodes=true
```

На втором компьютере:

```ini
node_id=2
expected_nodes=2
wait_for_nodes=true
```

После запуска первого компьютера программа покажет сообщение `WAIT` и будет ждать второй узел. Когда узлы обнаружат друг друга, обмен начнётся. Для трёх компьютеров укажите `expected_nodes=3` на каждом и назначьте каждому уникальный `node_id`.

Ожидание выполняется только перед началом измерений. После старта отключение участника не завершает прогон и не запускает ожидание заново. Если узел снова появится, программа продолжит обмен и добавит событие подключения в журнал.

## Журнал подключений и отключений

В конце ограниченного запуска (`max_cycles > 0`) выводится журнал изменений состава узлов, например:

```text
Connection log:
  Node 2 connected at cycle 0
  Node 3 connected at cycle 0
  Node 3 disconnected after 3000 cycles
  Node 3 connected after 9000 cycles
```

Событие отключения регистрируется не в момент физического отсоединения кабеля, а когда механизм Discovery обнаружит отсутствие маяков и удалит узел из списка активных. На это влияет `peer_timeout_ms`.

При `max_cycles=0` программа работает непрерывно; финальный журнал в текущей реализации печатается при завершении ограниченного прогона.

## Снижение задержек выхода процессора из простоя

Для уменьшения задержек, связанных с переходом CPU в энергосберегающие состояния простоя, в Linux можно временно задать ограничение latency через `/dev/cpu_dma_latency`.

Команда:

```bash
sudo python3 -c 'import os, time; fd = os.open("/dev/cpu_dma_latency", os.O_WRONLY); os.write(fd, b"\x00\x00\x00\x00"); time.sleep(86400)' &
```

Что делает эта команда:

1. Запускает Python от `root` в фоновом режиме (`&`).
2. Открывает `/dev/cpu_dma_latency` на запись. Этот интерфейс Linux позволяет процессу задать ограничение на допустимую задержку выхода CPU из состояния простоя.
3. Записывает значение `0` микросекунд в виде четырёх байтов. Это запрашивает минимально возможную latency для CPU idle.
4. Оставляет файл устройства открытым на 86400 секунд — 24 часа. Пока дескриптор открыт, запрос ограничения активен.
5. По истечении 24 часов процесс завершается, дескриптор закрывается и установленное им ограничение снимается. Оно также снимается, если процесс завершить раньше.

**Важно:** это не универсальная команда прямого отключения всех C-states. Она задаёт Linux latency QoS-запрос; драйверы cpuidle и платформа используют его, чтобы ограничивать состояния простоя с задержкой выхода выше запрошенного значения. Фактический эффект зависит от ядра, драйверов и оборудования. Значение `0` может существенно увеличить энергопотребление и нагрев, особенно на ноутбуках и серверах с высокой плотностью размещения. Используйте команду только на время тестов и контролируйте температуру и энергопотребление.

Проверить запущенный процесс можно так:

```bash
pgrep -af '/dev/cpu_dma_latency'
```

Чтобы снять ограничение раньше, завершите именно найденный процесс Python (по его PID):

```bash
sudo kill <PID>
```

После завершения процесса или истечения 24 часов запрос снимается автоматически. Команда не меняет настройки BIOS/UEFI и не сохраняет параметры после завершения процесса или перезагрузки.

## Настройки производительности процесса

В `config.ini` доступны:

- `cpu_affinity` — привязка основного потока к выбранному логическому CPU;
- `realtime_priority` — запрос планировщика `SCHED_FIFO`;
- `lock_memory` — запрос блокировки памяти в RAM через `mlockall`.

Для применения realtime-настроек программа обычно запускается через `sudo`. Если ядро или система не разрешает конкретную операцию, программа выводит предупреждение `WARN`; это не означает, что настройка успешно применена.

Настройка CPU affinity в текущей версии применяется к основному потоку процесса. Не следует считать её настройкой IRQ, сетевой карты или всех системных потоков.

## Интерпретация результатов

В терминале отображаются среднее время измеренного цикла, количество измерений, число циклов выше 200 мкс и гистограмма. Порог 200 мкс — индикатор для анализа, а не гарантия жёсткого real-time. На результат влияют планировщик Linux, драйвер сетевой карты, IRQ, коммутатор, загрузка CPU, энергосбережение и настройки сети.

Обычный Linux и UDP multicast не обеспечивают абсолютную гарантию максимальной задержки. Для корректного сравнения запускайте одинаковую конфигурацию и нагрузку, используйте одинаковый размер payload и проверяйте сетевой тракт.

## Устранение неполадок

- **Узлы не обнаруживают друг друга:** проверьте уникальность `node_id`, одинаковые `multicast_group` и `discovery_port`, правильный `interface_ip`, настройки firewall и поддержку multicast коммутатором/сетью.
- **Ошибка присоединения к multicast-группе:** проверьте, что `interface_ip` соответствует существующему IPv4-адресу активного интерфейса.
- **Программа долго показывает `WAIT`:** проверьте, что на всех компьютерах задано одинаковое `expected_nodes`, запущено нужное число экземпляров и discovery-пакеты проходят между узлами.
- **Предупреждения realtime или mlock:** проверьте запуск с нужными привилегиями и системные лимиты; предупреждение означает, что соответствующая настройка не была применена.
