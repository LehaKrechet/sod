# SOD Multicast

**SOD Multicast** — экспериментальный прототип на C++17 для обмена UDP multicast-данными между Linux-компьютерами по локальной сети Ethernet и измерения времени циклов обмена.

Программа отправляет сообщения заданного размера, разбивает их на UDP-фрагменты прикладного уровня, собирает фрагменты от других узлов и отображает информацию об обнаруженных участниках и распределении времени циклов.

> Это измерительный прототип, а не система гарантированного real-time. Значения времени зависят от ОС, сетевого адаптера, драйверов, нагрузки, настроек сети и других факторов. Порог 200 мкс используется как ориентир для анализа, а не как гарантия.

## Возможности

- UDP multicast-обмен между несколькими Linux-узлами.
- Настраиваемый размер сообщения: **1–100 KiB** (1024–102400 байт).
- Разбиение сообщения на части (chunks) и сборка на принимающем узле.
- Обнаружение узлов и отображение списка активных участников.
- Динамическая гистограмма времени цикла в терминале.
- Отображение среднего значения по накопленным измерениям.
- Запись измерений в CSV для дальнейшего анализа.
- Настройки сети, обмена и отображения через `config.ini`.

## Структура проекта

```text
sod_multicast/

    ├── config.cpp      # Чтение и проверка config.ini

    ├── network.cpp     # UDP multicast: отправка и прием фрагментов

    └── discovery.cpp   # Beacon-обмен и список активных узлов
```

## Требования

- Linux
- C++17-совместимый компилятор (например, GCC)
- CMake версии 3.16 или новее
- Ethernet-сеть, в которой разрешен multicast UDP

В Ubuntu/Debian необходимые инструменты можно установить:

```bash
sudo apt update
sudo apt install build-essential cmake
```

## Сборка

Из каталога проекта выполните:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

После сборки исполняемый файл находится в `build/sod_multicast`.

## Подготовка двух компьютеров

Подключите компьютеры к одной локальной Ethernet-сети. На каждом узле проверьте интерфейс и IPv4-адрес:

```bash
ip -br addr
```

Определите адрес Ethernet-интерфейса, например `192.168.67.3` на ПК №1 и `192.168.67.4` на ПК №2. Адреса приведены как пример — используйте адреса своей сети.

### Настройка ПК №1

В `config.ini` на первом компьютере установите уникальный `node_id`:

```ini
node_id=1
expected_nodes=2
interface_ip=192.168.67.3
```

### Настройка ПК №2

На втором компьютере параметры должны отличаться идентификатором узла и адресом интерфейса:

```ini
node_id=2
expected_nodes=2
interface_ip=192.168.67.4
```

Остальные параметры обмена на обоих компьютерах должны совпадать, в частности multicast-группа, порты и размер сообщения.

`expected_nodes` — общее число участвующих узлов, включая текущий компьютер. Для двух компьютеров задается `2`, для трех — `3` и так далее.

> `interface_ip` должен соответствовать IPv4-адресу сетевого интерфейса, через который планируется обмен. Если оставить `0.0.0.0`, программа использует выбор интерфейса по умолчанию, который может оказаться не тем, что требуется. Для теста через Ethernet рекомендуется указать адрес Ethernet явно.

## Запуск

Запустите программу на каждом компьютере из каталога проекта:

```bash
./build/sod_multicast config.ini
```

Если запуск выполняется из другого каталога, укажите путь к конфигурации явно. Например, из каталога `build`:

```bash
./sod_multicast ../config.ini
```

Запустите оба узла. В терминале обновляется панель с гистограммой, средним временем и обнаруженными узлами. Для завершения нажмите `Ctrl+C`.

## Параметры `config.ini`

| Параметр | Значение по умолчанию | Описание |
|---|---:|---|
| `node_id` | `1` | Уникальный ID текущего узла |
| `expected_nodes` | `2` | Общее количество узлов в тесте |
| `multicast_group` | `239.10.10.10` | Multicast IPv4-адрес группы |
| `data_port` | `5000` | UDP-порт передачи тестовых данных |
| `discovery_port` | `5001` | UDP-порт обнаружения узлов |
| `interface_ip` | `0.0.0.0` | IPv4 интерфейса для multicast |
| `payload_size_bytes` | `2048` | Размер сообщения в байтах (1024–102400) |
| `chunk_payload_bytes` | `1200` | Размер полезной части фрагмента (256–1400) |
| `cycle_period_us` | `1000` | Период цикла, микросекунды |
| `receive_timeout_us` | `120` | Время ожидания приема в цикле, микросекунды |
| `heartbeat_interval_ms` | `250` | Интервал beacon-обмена |
| `peer_timeout_ms` | `1500` | Время, после которого узел считается неактивным |
| `peer_status_interval_ms` | `1000` | Интервал обновления статуса узлов |
| `terminal_graph` | `true` | Включение терминальной гистограммы |
| `graph_width` | `48` | Ширина полос гистограммы |
| `graph_refresh_ms` | `100` | Частота обновления панели, миллисекунды |
| `csv_logging` | `true` | Включение записи CSV |

Проверки параметров размера сообщения и фрагмента выполняются при чтении конфигурации.

## Как устроен обмен

1. Каждый узел создает сообщение заданного размера.
2. Сообщение разбивается на части (chunks) в соответствии с `chunk_payload_bytes`.
3. Фрагменты отправляются по UDP multicast с идентификатором узла, номером цикла и индексами фрагментов.
4. Узлы принимают фрагменты других участников и собирают сообщение, проверяя номер цикла, размер и индексы.
5. По завершении или истечении времени ожидания программа рассчитывает показатели цикла.
6. В терминале обновляются среднее время, список активных узлов и гистограмма последних измерений.

## Файлы результатов

При включенном `csv_logging` в текущем рабочем каталоге создаются:

### `timing_cycles.csv`

Содержит данные по циклам:

| Поле | Описание |
|---|---|
| `seq` | Номер цикла |
| `payload_bytes` | Размер сообщения |
| `tx_us` | Время отправки в рамках измеряемого цикла |
| `rx_us` | Время приема/ожидания приема |
| `compute_us` | Время завершающего участка обработки |
| `total_us` | Полное измеряемое время цикла |
| `peers_received` | Количество узлов, сообщения которых собраны полностью |
| `expected_remote` | Ожидаемое число удаленных узлов |
| `over_200` | Признак превышения 200 мкс (`1` — превышено, `0` — нет) |

### `timing_packets.csv`

Содержит сведения о фрагментах собранных сообщений:

| Поле | Описание |
|---|---|
| `seq` | Номер цикла |
| `node_id` | ID отправившего узла |
| `chunk_index` | Индекс фрагмента |
| `chunk_count` | Общее число фрагментов сообщения |

CSV-файлы открываются в LibreOffice Calc, Excel или обрабатываются скриптами.

## Проверка сети и диагностика

Перед запуском проверьте адреса интерфейсов:

```bash
ip -br addr
```

Проверить маршрут до multicast-группы:

```bash
ip route get 239.10.10.10
```

При диагностике трафика (пример для Ethernet-интерфейса `enp3s0`):

```bash
sudo tcpdump -ni enp3s0 udp port 5000 or udp port 5001
```

Замените `enp3s0` на имя интерфейса вашей системы.

Если программа сообщает об ошибке multicast join, проверьте, что `interface_ip` действительно назначен выбранному интерфейсу, интерфейс активен, а настройки группы и портов согласованы на всех узлах. Также проверьте правила firewall и ограничения сети на multicast.

## Интерпретация результатов

- Гистограммы на разных компьютерах могут различаться: каждый узел формирует статистику на основании собственных локальных измерений.
- Порог **200 мкс** — заданный критерий сравнения. Сам по себе вывод гистограммы не доказывает гарантированное соблюдение временных требований.
- Неполученные фрагменты, несовпадение последовательностей, задержки планировщика и временная рассинхронизация запуска могут влиять на результаты.
- UDP не гарантирует доставку, порядок или повторную передачу пакетов. В текущем прототипе восстановление потерянных фрагментов не реализовано.
- При больших размерах сообщения они передаются несколькими UDP-пакетами, что увеличивает нагрузку и вероятность неполного приема.

Для повторяемых измерений рекомендуется использовать одинаковые конфигурации на узлах (кроме `node_id` и `interface_ip`), запускать тесты в сопоставимых условиях и сохранять CSV каждого запуска.
